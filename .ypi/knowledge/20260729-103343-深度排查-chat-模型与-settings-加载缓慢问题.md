## Reusable knowledge
# Summary

本任务排查并修复了 Chat 模型目录与 Settings 模型配置加载缓慢问题。主要瓶颈是 `/api/models` 重复创建 Runtime、provider/auth 读取与 refresh 扇出、AnyRouter 目录读取时隐式写盘，以及前端 Chat/Settings 未共享模型请求。

# Reusable knowledge

- 模型目录读取应使用离线、共享的 fixed-provider admin catalog；不要创建 session inference runtime，也不要在 GET 路径调用额外 `getAvailable()`。
- 服务端使用 epoch、single-flight、短 burst cache，并按 canonical `agentDir` 隔离 cache/pending，避免不同工作目录串用目录结果。
- AnyRouter catalog GET 必须纯读；bridge/auth reconcile 只允许在显式 mutation/bootstrap 路径执行，并对相同内容做 no-op。
- 客户端 Chat 与 Settings 应订阅同一个 catalog resource；使用 AbortController、generation guard、last-good 保护旧响应、失效和失败恢复。
- `/api/models` 构建失败返回固定非 2xx 错误（`model_catalog_unavailable`），不要返回 HTTP 200 空目录覆盖 last-good。
- 成功修改模型、认证、账号或价格配置后再推进 catalog epoch；失败 mutation 不失效。
- 性能达标后不要默认引入 CredentialStore parsed snapshot；先用计数器证明仍有必要。
- 实测 isolated catalog 冷启动约 491–744ms、warm p95 约 105–180ms、8 并发共享一次 flight。30142 首次请求包含 Next 编译约 2.7s，后续 `/api/models` 约 2–60ms，`/api/web-config` warm 约 4–10ms。
- 真实凭据 UAT、30142 进程级完整验证与浏览器 waterfall 仍需在 Browser Share/操作者环境可用时补做。
